# MTG Collection — project rules for Claude

## What this is
A Magic: The Gathering collection and deck tracker, shipped as TWO versions from ONE repository:

1. **Web version (PWA)** — hosted on GitHub Pages. Used by everyone, including iPhone users. Starts empty; each person's data lives only in their own browser storage. Never ships the owner's personal collection.
2. **Android app (APK)** — built from the same web code wrapped with Capacitor. Ships EMPTY like the web version (no personal data inside the APK). The owner loads their collection once by restoring a backup file (More → Backup). Can use native Android capabilities.

## The parity rule (important — the owner asked for this explicitly)
- The two versions have DIFFERENT capabilities. For every feature or change, always think about both versions and offer a solution for each.
- They do not need to be identical. The Android version is expected to be more robust (e.g. live database file on the phone, automatic backups, better camera/OCR, file access).
- Do NOT let them drift far apart. Keep one shared codebase for everything that can be shared, and put platform-specific behavior behind a small platform layer (`isNative()` checks), not in forked copies.
- If a change cannot be shared or worked around, STOP and ask the owner for explicit approval before making the versions diverge. Say what each version will do differently and why.
- One push updates both: the web site and the APK are built and published together by the same GitHub Actions run.

## Working agreements
- Never push to GitHub without the owner's approval of the change first.
- Never commit the owner's personal collection data anywhere in the repo or the APK. Their data is loaded only by restoring their own backup file; keep the backup format (.sqlite/.json) restorable on both versions.
- The owner's real data lives on their phone. Updates must never overwrite or reset existing user data (storage keys stay stable; the app only ever starts empty or from a restored backup).
- The owner is not very familiar with GitHub: explain steps plainly and carefully.
- Existing app behaviors to preserve: deck edits are staged (+/−/add) and only applied by “Save changes” with a confirmation, followed by a pull-list popup grouped by set source or deck, verified-artwork gold checkmark, source dropdown with "add new", sleeve palette/photo crop, AI deck builder (Option A copy/paste, Option B own API key — saved on the device it was typed on, per provider, in its own storage key `mtg_aikeys_v1` outside the collection data; never in share files; manual backups and device transfers ask before including keys, automatic backups always include them; restores only adopt keys for the same collection ID or an empty app and never overwrite a key already saved; “Remember my API key” can be switched off), backup to share sheet / .sqlite / .json.

## Build & release
- Web: GitHub Pages serves the repo root (index.html, sw.js, manifest, icons). Android: `.github/workflows/android.yml` wraps the same files with Capacitor (appId com.dakeera.mtgdeckmaster, name "MtG DeckMaster") and publishes a signed APK to Releases on every push to main.
- The APK must always be signed with the same key (GitHub secrets ANDROID_KEYSTORE_BASE64, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_ALIAS) so updates install over the old app and keep the user's data. Never change the appId or the key.
- Auto-backup (More → Backup, off by default): newest 5 JSON copies; Android writes files to Documents/MtG-DeckMaster/autosave, web keeps them in IndexedDB. Never touches manual backups.
- Back button: one shared `navBack()` in index.html (modals → in-tab steps → tab history → double-back to exit). Android hooks it to `@capacitor/app`; the web version uses a history sentinel.
- In-app updates (Android): `android-resources/native/` holds a local Capacitor plugin `ApkUpdaterPlugin.java`, a `MainActivity.java` that registers it, and `file_paths.xml`; the workflow copies them into the generated android project and adds `REQUEST_INSTALL_PACKAGES`. The app checks GitHub Releases (`android-v1.N` tags) at most once per 20 h and from More → App updates, downloads the APK into its cache, then opens Android's installer (the user must tap Install; first time also allow “Install unknown apps”). Web version: compares a hash of the live `index.html` + `features.js` with the loaded one and shows a Reload banner. Both banners offer a non-blocking “Back up now”.
- Android-only code goes behind `window.Capacitor?.isNativePlatform()`. The shared code is `index.html` (core app) plus `features.js` (deck draft editing, in-app camera, bulk import, other people's collections viewer, formats guide, battle simulator); both versions load the same two files. A new shared file must also be added to `scripts/build-www.js` and the `SHELL` list in `sw.js`.
- Identity: each collection has a permanent random ID (`D.uid`, shown as a short code), a changeable name (`D.owner`) and an ECDSA signing key (`D.keys`). No server or user database. IDs are only created by “Start my collection” or the first save, never changed by renaming, and restored with a backup. File names start with name + ID code.
- Two file kinds: full **backups** (private; include `D.keys`) and signed **share files** (`kind:'mtg-share'`; cards and decks only, never keys, logs, sleeves or acquisition data). Every file goes through `fxOpenFile`, which decides restore vs view and warns on other people's backups, older backups, changed files and signature mismatches (with trust / keep-both options). Never put `D.keys.priv` in anything that is shared or stored under Other collections.
- Deck links (`…/d/#d=…`) carry deck names only and are unsigned; they open view-only. `d/index.html` is the web landing page (tries the Android app via an `intent://` link, then falls back to the web version). The APK registers the `mtgdeckmaster://` scheme and the `https://dakeera.github.io/mtg-collection/d` App Link (workflow `sed` on AndroidManifest); fully automatic opening needs `android-resources/assetlinks.json` published at `https://dakeera.github.io/.well-known/assetlinks.json` (a separate `dakeera.github.io` repo).
- The fourth tab is called “Deck Generator” (internal view key is still `ai`). Deck types come from `DFMT` in features.js (Casual + official constructed formats + MTG Arena formats + community formats; Draft, Sealed, Cube, Jumpstart and Two-Headed Giant are deliberately excluded). The user must pick one (“↺ Start over” clears every option after a confirmation); commander suggestions use the same availability/legality/color filters as the card list (`aiCmdChoices`); its size, copy limit, commander rule and legality key drive the prompt, the reply check, deck targets and sleeves. Decks can also be built by hand: New deck → card picker (`fxBuilder`) → staged Save. Every deck format has rules built in: staged adds are blocked once the deck reaches the format size; banned / not-legal / restricted / too-many-copies / outside-commander-colors cards (color identity from `fxCI`: Scryfall `c.ci` when known, else every colored mana symbol in cost + rules text — never just the `colors` text, which can say e.g. “Colorless/Multi”) can still be added but are flagged (`fxCardIssues`, `deckIssues`), shown with ⚠ on the Decks list and an Inspect box on the deck page with staged fixes or “Ignore this” (`d.ok`; ignored issues stay listed, muted, with “Stop ignoring”). Formats with a legality key pause for a legality check (`ensureLegal(list)`) when a deck is opened or the picker starts; if offline the deck gets `d.legPending` (⏳ on the Decks list, “Check now” on the deck page), re-checked whenever the deck is opened, cleared once it succeeds. Cards Scryfall can’t match get `legMiss` (plus a fuzzy-match suggestion in `legSug`); the user can accept the suggestion, search (`fxMatchUnknown` — updates the EXISTING card via `renameCard`, never a duplicate) or mark it as a custom card (also creatable from scratch with “★ Add a custom card” on the Add card tab, `fxCustomNew`, and editable later with “✎ Edit card details”, `fxCustomEdit`; custom cards have no Printing row) (`c.custom`: its own group in the Collection filter, CUSTOM badge, skipped by all Scryfall lookups and data check, flagged as not legal in official formats, kept in share files). Opening a modal from another tab (e.g. “Build a deck by hand” on Deck Generator, multi-card add on Add card) must not switch tabs until something is actually created.
- ✨ Optimize Deck (deck page, next to “＋ Add cards”; Edit details / Share deck / Delete deck sit on the row below; Delete deck asks twice, the second time “Are you sure???”): `fxOptOpen` → `V.opt` view (`fxOptView`, state `OPT`) with the Deck Generator’s tools (legality for casual decks, colors — commander identity for commander decks, else the deck’s current colors unless the user picks colors —, where new cards may come from, only-own, Option A copy prompt, Option B shared provider/model/key via `aiKeyUI()`). The “How do you want to optimize?” goal works like Theme; blank = review the collection + deck for a more optimal build. The AI answers with `OUT n Card` / `IN n Card` lines + `---` + explanation; `fxOptRead` checks every line against the deck’s format rules (`fxRuleBlock`, copy caps, size, availability, commander stays). “Accept” shows a confirmation screen (removals on top grouped by where they go back to, additions below grouped by pull source/“From deck”), and “Update deck” applies it through the staged-draft save (`fxDraftSave({yes,allowed})`) followed by the usual pull list. The Deck Generator uses the same rule check (`fxRuleBlock` + size cap, commander color identity in the prompt) and the same grouped confirmation (`aiConfirm`) before creating a deck.
- Pop-ups: while any modal/full-screen layer is open the page behind can’t scroll (`fxLockCheck` toggles `html.lock`).
- Deck links: “Share as a link” makes a TinyURL short link (`fxShortUrl`: Android via CapacitorHttp, web via fetch, is.gd JSONP as web fallback) to `…/d/?d=<compact code>` (`fxPackDeck`, prefix `c`: `#set:number` for cards with a known printing, names otherwise, qty 1 omitted). The app-only link (`fxAppLink`, `…/d/#d=<code>`) is offered only when offline (checked at link time) or, when online, after TinyURL failed twice (first failure: Try again / Send as a file; second: app-only link / Send as a file; resets each time Share deck is opened). Pasted tinyurl/is.gd links are resolved on both versions (`fxOpenShort`; is.gd via its forward JSONP `fxIsgdLookup`, TinyURL via CapacitorHttp on Android, else by opening the link). Old `j`/`z` links still open. Compact links are signed with the collection key (`k:` public key + `s:` signature lines). On opening (`fxLinkImport`): a verified link joins that sender’s entry in Other collections (grouped by sender, same entry as their signed share files); an unsigned/altered link goes into a separate unverified “— shared by link” entry; a key clash with a known sender asks first and stays separate; a link signed with the user’s own key is treated as their own deck (opened, or offered to add if missing). Other people’s decks are shown as “Owner - Deck” (`fxDeckTitle`) on their deck pages, in Matchups and in share messages; Other collections rows list each sender’s decks.
- Rule override: adding a card that breaks the deck's format rules (including going over the card limit) is blocked unless the deck is in override mode; turning it on takes two confirmations in a row (`fxOverrideAsk`), once per deck (`d.override`). An overridden deck always shows a red “⛔ Override on” tag on the Decks list and a box on the deck page that open the full list of violations; it can be turned off, and it switches itself off automatically (`fxOverrideAuto`) once the deck has no rule issues left, so breaking a rule again needs two approvals again.
- Custom card photos: the 🎨 button on a custom card opens `fxCustomArt` (take a photo with the framed in-app camera, or upload a picture) — never the printing picker, Scryfall search or card scan (`artPicker`/verify redirect custom cards there). Pictures are compressed to ~60 KB JPEG (490×684), kept in IndexedDB (`mtg_imgs`, in memory as `CIMG`), never in localStorage. They are added to backups, auto-backups, device transfers and share files as `customImgs` (`fxWithImgs`) and read back with `fxImgsIn`.
- Foil: Scryfall images are non-foil scans, so finishes are shown with labels on artwork choices (`fxFinLabel`) and a ✦ FOIL tag plus rainbow shine on cards owned as foil (`fxHasFoil`).
- Suggestion lists: never rely on the browser's `<datalist>` popup (Android draws it see-through in dark mode). Any `<input list=…>` is converted automatically to the styled `.acbox` dropdown (`fxACWire`), so new suggestion lists can still be written as `<datalist>`. The list scrolls with a finger; an option is chosen only by a deliberate tap (pointer down and up on the same option without moving). Suggestion fields and search boxes inside pop-ups get a ✕ clear button (`.acw`/`.acx`) once they have text.
- The source “Custom Cards” is reserved: every custom card is filed under it (`CUSTOM_SRC`), it is never offered or accepted as a source for real cards (`isCustomSrc`), and it is never auto-numbered. “It’s a real card — unmark” asks for approval, then for an existing or new source (`fxUnmarkCustom`), which replaces Custom Cards on the card and its acquisition entries.
- “Add several cards at once” (Add card tab): after lookup, cards go through a card-by-card picker in the typed order (`fxQAPick`: choose the printing/artwork, finish and copies; misspelled names are matched with Scryfall’s fuzzy lookup and flagged “you typed …” with “Not right? Search again”; still-unknown names show “Did you mean” suggestions and can be searched again, scanned, or skipped), then the usual review and confirmation; the card name + copies/finish bar sticks to the top (`.qabar`) and Previous/Skip/Next stays fixed above the tab bar (`.qanav`) while the artwork scrolls. Tapping the set text under an artwork just selects it (highlight, stays on the screen, keeps the scroll position); tapping the picture opens it full screen (`fxQAView`, `#qafull`: ‹ › arrows and swipe through every printing, ↻ Flip for double-faced cards, “Use this one” / “Back to list”; the back button closes it first). The typed text is kept (`V.qadd`) until the cards are added, and the box has a ✕.
- Bulk imports (More → Bulk import and “Add several cards at once”) are always ONE source: the card’s set comes from the chosen printing, and the source is asked on the final check screen with the same picker as a single add (`srcFields`; `SQ()` returns `IMP.sq` while that screen is showing, else `A.q`). Nothing is added until a source is chosen; a file’s own Source column is not used. Cards whose printing was picked in the several-cards picker are added as verified ✓ (`fxAddCard(…,ver)`; an already-verified artwork is never replaced, and the picker preselects it). The WotC set/printing is stored on every card but only shown (card detail “Printing” row) once the artwork is verified.
- Verified artwork: every way a printing gets confirmed goes through `fxVerifyPrint` (sets printing + `verified:true` = gold ✓, logs the edit, refreshes price/art): artwork picker/scan (`useArt`), single add, several-cards picker, import-history verification, pull-source verification.
- Import history (`D.imports`, newest first; shown on More → Bulk import): every bulk / several-cards import is recorded (date, source, cards, chosen printing id). After a bulk import the app asks whether to verify artwork now; verification (`fxHistVerify` → `IMP.kind='verify'`, `fxVerPick`) saves each card as you go (“Save & next”, “Skip for now”, “Finish later”), so it can be partly done and resumed. Cards verified any other way count as done. Removing an entry never touches the cards.
- Pull-source verification (`fxSrcVerify`, runs once automatically when online — `D.srcv2` — and again after a restore if not done; button on More → Data check): an unverified card whose every pull source names a real set (longest Scryfall set-name match; booster sources limited to booster printings) and points to exactly one printing gets that printing verified. Scryfall calls go through `scry`/`scryFetch` (search/named/collection spaced ~2 per second, 429 waits and retries); the background check pauses while the user is looking cards up (`fxBusy`). Anything uncertain (several printings, Trade/Gift/Singles or non-set sources, mixed sources) stays unverified and is listed with the reason.
- New manually typed sources are auto-numbered (“Mystery Box” → “Mystery Box 1”, next pull “… 2”); Trade, Gift and Singles Orders are never numbered.
- Other people's collections are view-only: while one is open (`RO` set) `persist()`/`save()`/`saveArt()` do nothing, so the owner's own data can never be overwritten. Keep that guard.
- When a scan or printing change reveals that an existing entry's data is wrong, the app asks for approval and UPDATES THE EXISTING CARD. It must never create a duplicate card for that.
